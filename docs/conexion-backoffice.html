Cómo conectar su back office con la web

Esta web es solo la vidriera (el front). Productos, precios, stock y pedidos se manejan en el back office de ustedes, y la web los muestra.

La idea

Su back office

Lo que ya tienen · manda en los datos
  • Productos, fotos, colores y talles
  • Precios, ofertas y stock
  • Categorías
  • Banners y promos de cuotas
  • Pedidos: recibirlos, prepararlos, despacharlos
datos → ← pedidos aviso de cambio →

Esta web (front)

Lo que hicimos acá · muestra y vende
  • Inicio, catálogo, filtros y buscador
  • Ficha de producto y cuotas
  • Carrito, favoritos y checkout
  • Cobro con tarjeta y cotización de envío
  • “Seguí tu pedido”

La web no guarda productos propios: cada vez que necesita mostrar algo, se lo pide al back office. Si cambian un precio allá, se ve acá. El panel /admin que trae la web queda apagado o, si prefieren, solo para lo que su back office no maneje (por ejemplo banners).

Las 3 conexiones

1. La web lee los datos

Web → back office

Su back office expone una API de lectura (ver la tabla de abajo). La web la llama desde su servidor, nunca desde el navegador del cliente, y guarda una copia por unos minutos para que la tienda ande rápido aunque haya mucho tráfico.

De su lado: crear esos endpoints. Del mío: hacer el adaptador que convierte su formato al de la web. Si su API ya existe con otro formato, me adapto yo.

2. El back office avisa que algo cambió

Back office → web

Cuando guardan un cambio, su back office hace una llamada corta a la web y la web borra su copia de ese dato, así el cambio se ve al instante. Este endpoint ya está hecho:

POST https://<dominio-de-la-web>/api/revalidate
x-revalidate-secret: <CLAVE_AVISO>
Content-Type: application/json

{ "table": "products", "record": { "slug": "zapatilla-urbana-negra" } }

Valores de table: products, categories, home_banners, payment_promos, topbar_messages, settings. Si no mandan el aviso igual funciona: la web se actualiza sola cada pocos minutos (categorías y datos del local, cada algunas horas).

3. La web manda los pedidos

Web → back office

Cuando alguien compra, la web:

  1. Le pregunta al back office si hay stock de cada talle y color (o reserva el stock).
  2. Cobra con la tarjeta (Payway).
  3. Le manda el pedido completo al back office: cliente, productos, envío, pago y total.

Desde ahí el pedido lo maneja su back office: descuenta stock, lo prepara y lo despacha. Para “Seguí tu pedido”, la web le pregunta el estado y el número de seguimiento al back office.

Qué datos necesita la web

Este es el formato que propongo. Si su API devuelve otra cosa no hay problema: me pasan un ejemplo y lo adapto.

Seguridad

  • Todo por HTTPS y de servidor a servidor. Las claves nunca llegan al navegador del cliente.
  • Una clave para cada sentido: una que la web usa para llamar a su back office (header Authorization: Bearer …) y otra para el aviso de cambios. Se guardan como variables de entorno, no en el código.
  • La API de lectura puede ser solo de lectura. La única escritura que hace la web es crear pedidos.
  • Las fotos quedan en su servidor o CDN. Me pasan el dominio y lo agrego a la lista de permitidos de la web.

Pasos

  1. Ustedes me pasan la documentación de su API o un ejemplo de respuesta de productos, categorías y pedidos.
  2. Yo hago el adaptador en la web y apago la carga de productos del panel /admin.
  3. Juntos definimos las URLs y generamos las claves de cada lado.
  4. Su programador agrega el aviso de cambios al guardar en el back office.
  5. Probamos en una versión de prueba: cambiar un precio, ver que aparece; hacer una compra de prueba, ver que llega el pedido.
  6. Publicamos con el dominio real.

Si su back office no puede exponer una API, hay otra opción que ya está hecha: su back office le manda cada cambio a la web por la API de la web (/api/admin/v1, documentada en docs/API.md). Funciona, pero hay dos copias de los datos que tienen que mantenerse iguales, por eso es la segunda opción.

Qué necesito de ustedes

  1. ¿En qué está hecho su back office y tiene API? Documentación o ejemplos de respuesta.
  2. ¿Dónde están las fotos de los productos (dominio)?
  3. ¿Los banners y promos de cuotas los cargan en su back office o los dejamos en el panel de la web?
  4. ¿Quién cobra: la web con Payway y les avisa, o su sistema?
  5. ¿Quién cotiza y genera los envíos con Andreani y Correo Argentino: la web o su back office?
  6. ¿Cómo identifican cada talle y color (SKU)? Es la llave para el stock y los pedidos.
